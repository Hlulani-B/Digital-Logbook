## Architecture

This monorepo contains independent backend services, a root-level API Gateway, and a React frontend. Each service runs as its own process on its own port.

```text
codacaine/
├── frontend/                       # React application (Vite)
│   ├── src/
│   ├── Dockerfile
│   ├── package.json
│   └── .env
├── api-gateway/                    # Entry point for backend API requests
│   ├── src/
│   │   └── index.js
│   ├── Dockerfile
│   ├── package.json
│   └── .env
├── services/
│   ├── auth-service/               # Login/signup via Supabase Auth
│   │   ├── index.js
│   │   ├── Dockerfile
│   │   ├── package.json
│   │   └── .env
│   ├── dashboard-service/          # Cross-project summaries
│   │   ├── index.js
│   │   ├── Dockerfile
│   │   ├── package.json
│   │   └── .env
│   ├── project-service/            # Project entries, timeline, search, stats
│   │   ├── index.js
│   │   ├── Dockerfile
│   │   ├── package.json
│   │   └── .env
│   └── profile-service/            # User profile management
│       ├── index.js
│       ├── Dockerfile
│       ├── package.json
│       └── .env
├── docker-compose.yml              # Docker multi-container configuration
├── .gitignore
└── README.md
```

## Prerequisites

- Node.js (LTS) and npm
- A Supabase project (URL + API key)
- Git
- Docker and Docker Compose (optional, for containerized deployment)

## Getting Started

### 1. Clone the repo

```powershell
git clone https://sdp.ms.wits.ac.za/codacaine/Digital-Logbook.git
cd Digital-Logbook
```

### 2. Install dependencies for each service

From the repository root:

```powershell
cd services\auth-service
npm install
cd ..\dashboard-service
npm install
cd ..\project-service
npm install
cd ..\profile-service
npm install
cd ..\..
```

### 3. Install API Gateway dependencies

```powershell
cd api-gateway
npm install
cd ..
```

### 4. Install frontend dependencies

```powershell
cd frontend
npm install
cd ..
```

## Environment Variables

Each backend service and the API Gateway needs its own `.env` file. These files are excluded from version control through `.gitignore` because they contain secrets. Each teammate must create their own local copies.

Create the following files:

- `services/auth-service/.env`
- `services/dashboard-service/.env`
- `services/project-service/.env`
- `services/profile-service/.env`
- `api-gateway/.env`
- `frontend/.env` (as required by your frontend configuration)

### Backend services

Use the Supabase URL and key supplied by the team lead or Supabase project settings. Example:

```dotenv
SUPABASE_URL=https://yourproject.supabase.co
SUPABASE_KEY=your_supabase_key
PORT=4001
```

Use the same Supabase project settings across the services that require them, but give each service a distinct port when running locally according to this README:

| Service | Port |
| :------ | ---: |
| auth-service | 4001 |
| dashboard-service | 4002 |
| project-service | 4003 |
| profile-service | 4004 |
| api-gateway | 4000 |

### API Gateway (`api-gateway/.env`)

```dotenv
PORT=4000
AUTH_SERVICE_URL=http://localhost:4001
DASHBOARD_SERVICE_URL=http://localhost:4002
PROJECT_SERVICE_URL=http://localhost:4003
PROFILE_SERVICE_URL=http://localhost:4004
```

The frontend sends API requests through the gateway using `/api/auth`, `/api/dashboard`, `/api/project`, and `/api/profile`.

For a frontend configuration that supports it, set:

```dotenv
VITE_API_GATEWAY_URL=http://localhost:4000
```

**Do not commit secret keys or database credentials to the repository.**

## Running the Project

Run each backend service in its own terminal, starting from the repository root:

**Auth Service**

```powershell
cd services\auth-service
node index.js
```

**Dashboard Service**

```powershell
cd services\dashboard-service
node index.js
```

**Project Service**

```powershell
cd services\project-service
node index.js
```

**Profile Service**

```powershell
cd services\profile-service
node index.js
```

**API Gateway**

```powershell
cd api-gateway
npm start
```

**Frontend**

```powershell
cd frontend
npm run dev
```

### Running with Docker Compose

With the Dockerfiles and `docker-compose.yml` in place, run the following command from the repository root:

```powershell
docker compose up --build -d
```

To stop the containers:

```powershell
docker compose down
```

> Docker Compose uses its own service configuration and internal network addresses. Ensure that the ports and environment variables in `docker-compose.yml` match the application configuration when running in containers.

## Branching Rules

- `main` and `services` branches are protected — no direct pushes. Changes must go through a pull request with required approvals.
- Create a feature branch for your work:

```powershell
git checkout -b feature/your-feature-name
git add .
git commit -m "describe your change"
git push -u origin feature/your-feature-name
```

Then open a pull request on Gitea into `main` (or `services` for backend-only work).

## Rule: Dashboard vs Project Data

- Project entries and their statistics stay scoped to that project (`project-service`).
- The dashboard (`dashboard-service`) only shows cross-project summaries — it does not read individual entry tables directly.
