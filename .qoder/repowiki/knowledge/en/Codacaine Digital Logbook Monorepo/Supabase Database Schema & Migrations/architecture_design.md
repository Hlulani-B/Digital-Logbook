The module is split into two layers. `setup.sql` is a one-shot bootstrap script intended to be run once in the Supabase SQL Editor; it creates core tables (`users`, `activity_log`), account-deletion RPCs (`delete_user`, `restore_user`, `purge_deleted_users`), backfills existing auth users, registers pg_cron jobs for nightly purges, and defines analytics RPCs (`get_project_stats`, `get_field_stats`). `migrations/` holds numbered, ordered, idempotent DDL migrations (000–011) that capture incremental changes on top of the baseline full schema in `000_baseline_full_schema.sql`. The baseline migration recreates every table, enum (`priority_level`), index, constraint, trigger (`on_auth_user_created` on `auth.users`), and RPC from scratch using `CREATE TABLE IF NOT EXISTS` / `CREATE OR REPLACE FUNCTION` so it can be re-run safely against any state. Domain tables are organized by service boundary: `users` (profile-service), `projects` + `entries` + `fields` (project-service), plus cross-cutting tables (`activity_log`, `health_ping`, `ai_provider_cooldowns`, `notes`, `notifications`). Business logic lives in PL/pgSQL functions marked `SECURITY DEFINER` that operate on `auth.uid()` to enforce row-level ownership without application-side checks. Scheduling is handled entirely via pg_cron jobs registered inside migrations (e.g., purge deleted accounts, purge unconfirmed sign-ups, due-notification cycle). The notification subsystem (migration 011) integrates with pg_net to POST pending emails to an external project-service endpoint, degrading gracefully when pg_net is unavailable.
