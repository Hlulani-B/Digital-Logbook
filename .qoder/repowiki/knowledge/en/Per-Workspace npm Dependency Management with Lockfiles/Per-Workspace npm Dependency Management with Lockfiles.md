## What system/approach is used

The repository uses **npm** as the package manager across all JavaScript/TypeScript workspaces, with each workspace maintaining its own `package.json` and a committed `package-lock.json` lockfile (lockfileVersion 3). There is no monorepo tool (no `pnpm`, `yarn`, `lerna`, `nx`, `turborepo`, etc.) — instead it is a flat directory layout where the root `package.json` only declares shared dev tooling (Prettier, Husky, lint-staged) and per-workspace packages live under `frontend/` and `services/<name>/`. Python dependencies for the docs site are managed separately via `docs-site/requirements.txt`.

## Key files and packages

- **Root manifest**: `package.json` — private workspace declaring Prettier, Husky, lint-staged; scripts for DB migration/backup/restore.
- **Frontend manifest**: `frontend/package.json` — React + Vite + TypeScript app; runtime deps include `@supabase/supabase-js`, `react`, `react-router-dom`, `idb`, `sql.js`; dev deps include Vitest, testing-library, ffmpeg tooling.
- **Service manifests**: `services/auth-service/package.json`, `services/dashboard-service/package.json`, `services/profile-service/package.json`, `services/project-service/package.json` — Express-based Node services sharing common deps (`cors`, `dotenv`, `express`, `pg`) plus service-specific ones (e.g. `jose`, `openai`, `@google/generative-ai`, `@huggingface/inference`, `@cerebras/cerebras_cloud_sdk`, `sharp`, `swagger-ui-express`).
- **Lockfiles**: `package-lock.json` at root, `frontend/package-lock.json`, and one `package-lock.json` per service — all committed to version control.
- **Python docs deps**: `docs-site/requirements.txt` listing `mkdocs` and `mkdocs-material`.
- **Deployment config**: `render.yaml` drives install/build per service (`npm install` / `pip install -r requirements.txt && mkdocs build --strict`), confirming npm is the expected resolver on Render.
- **Ignored artifacts**: `.gitignore` excludes `node_modules/` and `coverage/`, so dependencies are installed fresh from lockfiles on every build.

## Architecture and conventions

1. **One `package.json` per workspace** — the frontend and each of the four backend services (`auth-service`, `dashboard-service`, `profile-service`, `project-service`) declare their own dependencies independently. There is no shared `packages/` folder or workspace protocol between them.
2. **Lockfiles are committed** — every workspace ships a `package-lock.json` (lockfileVersion 3), pinning exact transitive versions for reproducible installs.
3. **Semver ranges use caret (`^`)** — all declared dependencies in every `package.json` use `^` ranges (e.g. `"express": "^5.2.1"`, `"react": "^19.1.0"`), allowing minor/patch updates while keeping major-version stability.
4. **No vendoring** — `node_modules/` is gitignored; nothing is vendored into the repo. Dependencies are fetched from the public npm registry at install time.
5. **No private registries or `.npmrc`** — no `.npmrc`, `pnpm-workspace.yaml`, or custom registry configuration was found; installs resolve against the default npm registry.
6. **Python side is separate** — the docs site uses pip with a flat `requirements.txt` (no `pyproject.toml`, no Poetry/Pipenv lockfile).
7. **Dev-only tooling is co-located** — formatting (Prettier), pre-commit hooks (Husky + lint-staged), and per-service test runners (Jest/Babel, Vitest) are declared as `devDependencies` inside their respective workspaces.
8. **Build/deploy pipeline assumes npm** — `render.yaml` runs `npm install` for every Node service and `pip install -r requirements.txt` for the docs site, so CI/CD depends on these manifests being up-to-date with the lockfiles.

## Conventions and constraints

- Each workspace must keep its `package.json` and matching `package-lock.json` in sync; deployments will fail if they diverge because Render runs `npm install` against the committed lockfile.
- New third-party libraries should be added to the appropriate workspace's `dependencies` or `devDependencies` using caret ranges (`^major.minor.patch`), then regenerated by running `npm install` to update the lockfile.
- The root workspace is intentionally minimal: it only holds cross-cutting dev tooling (Prettier, Husky, lint-staged) and database utility scripts; application code lives exclusively in `frontend/` and `services/*`.
- Environment-sensitive packages (e.g. native modules like `sharp`) are treated like any other dependency — installed from the registry during the build step defined in `render.yaml`.
- No global/shared dependency policy document was found; the de-facto rule is "one `package.json` per deployable unit, lockfile committed alongside it".
